# Chores

Low-priority cleanup and tech-debt items. Not blocking, but worth doing.

## Open

- **Band ownership is stored twice and only one path keeps the two in step.** `band.ownerId` (`src/lib/server/db/schema/band.ts`) duplicates the `band_member` row whose `role` is `'owner'`, and nothing in the database ties them together — SQLite has no cross-table constraint, so the agreement is upheld by convention at every site that inserts a band. `create()` (`src/lib/server/band/band-service.ts`) writes both in one `db.batch` and is the only runtime path that does; both seeds hand-write the pair correctly, which is exactly why the drift stayed invisible for so long — every environment a developer looks at is healthy. The Postgres migrator took `band.owner_id` from one legacy table and member roles from another with no reconciliation, and 5 of 16 production bands lost their owner as a result: three had the owner demoted to `admin`, two had no member row at all. Since `requireBandOwner` resolves through `requireBandMember()` and reads only `band_member.role`, those bands silently lost all nine owner-only capabilities — delete, transfer, address change, the three subscription forms and the three custom-domain forms — and the Settings nav item with them. That data is repaired and a partial unique index now caps a band at one owner row, but the index cannot enforce that a band has _at least_ one owner, nor that the row agrees with `band.ownerId`; both remain code-level conventions. The real fix is to delete the column and derive ownership from `band_member`, which is where the security boundary already reads. Two things to handle on the way: roughly a dozen read sites, several of them `innerJoin(user, eq(user.id, band.ownerId))` in the staff band lists and the band-site loader, where the join is genuinely convenient and becomes a subquery or a filtered join; and `user-service.ts` refuses to soft-delete a user who owns a band by querying that column, so the guard has to move with it. Also note `transferOwnership` is scoped by an `actorId` that the staff wrapper (`bands.remote.ts`) feeds from `band.ownerId` — if the two ever disagreed the demote matched zero rows, which is the second way a band ends up with two owners or none. One sequencing question before starting: `docs/specs/groups-spec.md` proposes replacing the `band` table outright — splitting it into `group` + `directory_entry` + `band_site` — which would delete `band.ownerId` as a side effect and redo every read site this chore touches. Doing the chore first is right only if groups is far off; neither document said so until `docs/reports/spec-audit.md` noticed the overlap.

- **Restricting a member for a reason that isn't misconduct has nowhere to live but moderation.** `setMemberStanding` (`src/lib/remote/standing.remote.ts`) exists for one documented case: switching messaging off for the occasional under-18 member, "since the site has no age of its own". It writes `member_standing` with `scope: 'messaging'`, `status: 'disabled'` — the same table, ladder and staff card as someone restricted for abusing DMs. That is a category error: eligibility is a fact about who a member is, moderation is a judgement about what they did, and today they are indistinguishable to staff reading the card and to the member reading the notice. `docs/specs/moderation-appeals-spec.md` makes it visible rather than causing it — under that spec every `member_standing` write is a report someone can appeal, so a minor would be shown a report about their age and offered an appeal against their own date of birth. The spec evicts the case rather than accommodating it, which leaves it homeless until this is fixed. The root gap is that `user` carries no date of birth or age at all (`src/lib/server/db/schema/authentication.ts`), so "this member is a minor" is only ever a staff member remembering. Worth considering: a DOB (or an over-18 boolean, if storing a birthdate for minors is itself unattractive) with capability derived from it, so the restriction re-applies itself rather than depending on whoever took the signup call; or a `member_capability` table if more non-moderation gates turn up — under-18 messaging is unlikely to be the only one, given the space, the equipment loans and the volunteering all have plausible age or eligibility rules. Two things not to break on the way: `direct-service.ts` gates both sending and receiving on `status === 'disabled'`, so any replacement has to be read by the same two call sites; and `disabled` keeps a genuine moderation use as the escalation past reply-only `restricted`, so the rung stays — it is the age case that is the wrong occupant, not the rung.

- **Four component pairs do the same job under different names.** `shared/FreeformTagInput.svelte` vs `shared/Form/TagInput.svelte` (one takes free text, one takes an option list, neither says so); `shared/directory/ProfileLinks.svelte` vs `shared/directory/profile/LinksBox.svelte`, which carry near-identical `iconMap` records; and a `shared/reservations/` directory alongside a top-level `reservations/`. Also `member/membership/index.ts`, a barrel with zero importers. None of it is broken — it just means a new page picks whichever it finds first. Found during the template audit (`docs/development/template-audit.md`); untangling them is a rename-and-delete job, not a design question.

- **There are two tab systems.** `TabBar` renders `join-item btn` (a button group), while `src/routes/layout.css:373` separately overrides daisyUI's own `.tab` / `.tab-active`. Whichever a page reaches for, the other one's styling is dead weight. Decide which is the app's tab, then delete the other.

- **There is no platform ban, only deactivation.** `deactivateUser` (`src/lib/server/user/user-service.ts:60`) is the only way to remove someone, and it doubles as the member's own self-delete — both write `user.deletedAt`, so nothing distinguishes "they left" from "we removed them". It takes a user id and nothing else: no acting staff id, no reason, so a removal leaves no record of who decided or why (`deactivateUsers` tracks `skipUserId` so staff don't catch themselves in a batch, but still doesn't record the actor). It is simultaneously heavier than a ban should be and lighter than one needs to be: it cancels the user's future personal reservations and their Stripe subscription, and `reactivateUser` (:142) restores neither — while nothing stops the same person registering again the next minute, since there is no email or identity blocklist. Enforcement is sound: `hooks.server.ts:53` re-resolves every request and treats a deactivated user as anonymous, and their sessions are deleted on the way out. What's missing is the record and the gradations, not the kill switch. Direct messages added a standing ladder (`restricted` → `disabled`, now the `messaging` scope of `member_standing` after #224 merged the three per-domain tables) below deactivation, which covers messaging harms; a real ban has to answer re-registration, retention and appeal, and touches reservations, events, directory and billing, so it wants its own spec rather than a column.

- **Notification email content is built at every call site, not by the email service.** `dispatch` (`src/lib/server/notification/dispatcher.ts`) centralizes the parts that are about _delivery_ — preference lookup, in-app row, SSE push, Postmark send, error capture — and says outright that it "does NOT know about specific notification types". Everything about _content_ is left to the caller: ~23 hand-built `emailTemplate.model` literals across `notification-listeners.ts` and `register-listeners.ts`, each restating its own subject, heading, paragraphs and quote. `NOTIFICATION_TYPES` (`src/lib/server/db/schema/notification.ts`) carried only routing metadata — `defaults`, `mandatory` — so there was nowhere to say "this type never includes member-authored text". Direct messages added one flag (`emailOmitsUserContent`, stripped in `normalizeNotificationModel`) to cover their own case, but that is one rule, not the general fix. The pattern is already in the codebase: `normalize-model.ts` exists precisely so listeners "don't each have to remember" three derived fields. Generalising that — moving per-type content policy onto `NotificationTypeDef` and reducing listeners to data — is the chore. Watch for the two non-generic aliases (`ticket-confirmation`, `inbox-reply`), which bypass `normalizeNotificationModel` entirely and would need their own arm.

- **The staff inbox can't tell you which colleague replied.** `ThreadTimeline` puts a message on the right either because the viewer wrote it (`viewerUserId` passed, as the member pages and flag triage do) or because it's `outbound` (no `viewerUserId`, as the staff inbox does) — `src/lib/components/inbox/ThreadTimeline.svelte:53`. The staff inbox uses the second deliberately: the argument in `member-portal-chat-spec.md` is that a colleague's reply must still read as _ours_, and it does. The cost is that every staff reply looks identical, so you can't see at a glance who answered a contact — the author is on the row (`author_user_id`, `author_name`) and simply isn't shown. Direct messages don't need this fixed, since both member pages pass `viewerUserId`. Worth deciding separately whether the staff inbox should keep organisation-side orientation and add an author label to each outbound bubble (probably this), or switch to author orientation and lose the "one voice" reading. Don't just flip the axis — `ThreadTimeline.svelte.spec.ts` pins both modes against each other because a change that fixes one view silently breaks the other.

- **Volunteer interest is no longer searchable across roles.** `/staff/volunteer/interest` was folded into `/staff/volunteer/roles` — per-role counts became a column and "who wants to do this" became the role detail page. What went with it was the ability to search any member by name/email and see every role they picked. That view belongs on the users table: add a role filter and an "interested in" column to `/staff/users`, backed by `listInterestedMembers` in `src/lib/server/volunteer/volunteer-interest-service.ts` (its role filter is an EXISTS, so a filtered member still comes back with all their roles).

- **Signup doesn't link an existing subscriber to the new account.** Nothing in `src/lib/server/auth.ts` attaches a `subscriber` row to a `userId` at registration. Linking only happens lazily — `findOrCreateForUser` when the member touches their account subscriptions, staff bulk-add, or `ensureSubscribersForUsers` when a built-in audience sends. So someone who joins the newsletter as `alice@x.com` and later registers with that address sees an empty list on their account page, because `getSubscriptionsForUser` looks up by `userId`. It self-heals on the first built-in send, but a better-auth `databaseHooks.user.create.after` calling `findOrCreateForUser` would close the window. Watch for the same address already linked to a different account.

- **A conflicting reservation is a quiet warning, not a stop sign.** `ConflictWarnings` renders an `alert-warning` line and flips the submit button to "Create with Override" — the same treatment whether the space is double-booked or the booking merely falls outside operating hours. On the practice-space interfaces (`CreateEventModal`, the event edit page's rebook panel, and the member/staff reservation forms) an actual overlap with a confirmed booking should be loud and distinct: `alert-error` rather than `alert-warning`, the conflicting booking's owner named, and the override gated behind a deliberate second action rather than sharing the primary submit. Worth separating `hasConflicts` into "overlaps an existing booking" and "outside normal hours" first — today `ConflictWarnings` conflates them into one flag (`src/lib/components/shared/reservations/ConflictWarnings.svelte`), so anything reading it cannot tell a double-booking from a late night.

- **A credited band can't ask for a fix to a listing it's on.** `event_band` lets an event's owner credit another platform band, and that band's only replies are `confirmLineupSlot` / `declineLineupSlot` (`src/lib/server/event/event-service.ts`, surfaced as the invite inbox on `src/routes/band/[slug]/events/+page.svelte`). There's no way to say "the date is wrong" or "that's not how we spell it" — the choice is accept a bad listing or decline and disappear from a bill you're actually playing. Community listings sharpen this: the listing may now be authored by someone with no connection to the band at all. Wants a third action, "Request a correction", carrying a note to whoever owns the event — plausibly as an inbox thread rather than new machinery. Granting credited bands direct edit rights is the wrong fix: it would let any act on a bill rewrite another party's listing.

- **A band can see that it booked the room, but not the booking.** There is no `band/[slug]/reservations/[id]`, so a band member gets a card in a list and nothing behind it — while staff (`/staff/reservations/[id]`) and the individual who booked it (`/member/reservations/[id]`) both get a full record. `entityHref` already says so out loud: the reservation arm routes the band panel to `/band/[slug]/reservations`, the list, with the comment that it "is the closest thing it has to a detail page". The three reservation cards (`band/[slug]/+page.svelte` and both tabs of `band/[slug]/reservations/+page.svelte`) are already `EntityIdentity` and already carry a full `ReservationRef`, so they render an unlinked title today and start linking the moment the route exists — nothing on those pages needs to change. What is missing is the destination: a band member wanting the notes, the payment state or the cancellation reason on one of their own bookings has to ask staff. A route guarded by `requireBandMember` showing what the band is entitled to see (not the booker's contact details or payment instrument) would close both; `toReservationRef` already carries `bandId`/`bandSlug`, so `entityHref`'s band arm is a one-line change once the page exists.

- **A booking is drawn as two different cards.** `member/reservations/ReservationCard.svelte` is art-directed — a tear-off date block (day / big date / month) tinted per status by component CSS, a "Today / Tomorrow / This Week" ribbon, the door code once confirmed, and a payment line from `ReservationSummary` (price, paid, refunded, overdue, "free hours available") above a member action row: cancel, confirm, confirm-waitlisted, pay. The band panel's three cards (`band/[slug]/+page.svelte` and both tabs of `band/[slug]/reservations/+page.svelte`) are `EntityIdentity size="md"` plus a status badge and Cancel, and their query does not even select `price`, `paidAt`, `cashDueCents` or `lockCode`. So the same record reads as two objects depending on which panel you are in. The direction to converge is _toward_ the art-directed card, not away from it: the date block and status tinting are the treatment worth having, and the band card should grow into them rather than the member card flattening into the shared tier. That is a design job, not a refactor — a band member seeing "Pay online" or the door code for a booking made on the band's behalf is a product decision, so the shared piece is the identity and the date block, not the action row. Not a priority; noted so the two do not drift further apart in the meantime.

- **Reservation times render in two different timezones.** `$lib/utils/format` pins `DEFAULT_TIMEZONE` on every formatter it builds (`venue()`), so a booking's hour is the club's hour everywhere it is formatted through that module — tables, chips, `toReservationRef` titles. But `ReservationSummary` (`src/lib/components/shared/reservations/`), `member/reservations/ReservationCard.svelte`, `member/reservations/+page.svelte` and `ManageRecurringReservations.svelte` format with `date-fns` `format()`, which has no timezone and uses the reader's. For anyone outside Pacific the two disagree: the row says 5:00 PM and the card, or the confirmation modal over it, says 8:00 PM. `ReservationSummary` is the widest exposure — eight action components use it (`CancelReservationAction`, `CompReservationAction`, `CompleteReservationAction`, `NoShowReservationAction`, `RefundReservationAction`, `CashReceivedAction`, `PayReservationAction`, `ConfirmWaitlistedAction`), which put it in front of staff as well as members, at exactly the moment someone is confirming they have the right booking. The fix is to route those through `$lib/utils/format` rather than `date-fns`; watch for the relative strings (`formatDistanceToNow`, "Due in 3 days") which have no venue-time equivalent yet.

## Done

- **Two checkouts raced for one port, and overlapping e2e runs produced meaningless failures.** The entry below closed the _state_ half of this and reasoned that what remained "collides on port 4173 first" — a collision being treated as sufficient protection. It is not, for two reasons. A collision is only loud if something is listening at the moment you look: `reuseExistingServer` short-circuits on whatever answers, and `e2e/global-setup.ts` samples `/_app/version.json` exactly once, so a server that dies or is replaced mid-run is never noticed (the symptom is `ERR_CONNECTION_REFUSED` partway through). And a port collision does nothing at all about the failure that actually matters: two suites that _do_ stay out of each other's way still compete for CPU, and these assertions are load-dominated. Measured 2026-08-23 with a sibling worktree's `vite preview` and workerd running alongside: 23 failures in one suite and 33 in the other, failure sets barely intersecting, whole spec files flipping between runs — every one of them environmental, none a regression, and nothing in the output saying so. Split into the two things it actually is. Ports are now per-checkout (`scripts/lib/checkout-ports.ts`): the main checkout keeps :5173/:4173 so the tracked `.claude/launch.json` and the docs stay honest, a worktree gets a stable pair hashed off its path, and vite binds with `strictPort` so a real collision fails loudly instead of bumping onto a neighbour's next port. Both `playwright.config.ts` and `vite.config.ts` derive that number independently, from two spellings of the same directory, so the hash normalises its input — un-normalised they disagree and Playwright polls a port nothing ever binds, which `scripts/lib/checkout-ports.spec.ts` pins. Concurrency is then refused outright rather than isolated: `e2e/lock.ts` takes a machine-wide lock in `prepare.ts`, hands it to `run.ts`, and names the holding checkout if a second run starts — before it spends five minutes building. The handoff is the subtle part, since `pnpm test:e2e` is two processes: `prepare.ts` deliberately does _not_ release on exit, so the lock it leaves has a dead pid that only a `run` from the same checkout may adopt, and anything dead for over a minute is stale.

Both steps now live at `src/lib/components/shared/reservations/booking/`, and the action imports them as `../reservations/booking/ConfirmStep.svelte`.

- **`src/stories/` was unmodified Storybook scaffolding.** ~190 lines of the generator's sample project (`Button`, `Header`, `Page` plus their CSS), unrelated to this app and unreferenced by it. Deleted; the app's real stories live next to their components, and the Storybook sidebar no longer carries a second, misleading `Button`.

- **The e2e suite lost one random test per run to a workerd SQLite lock.** Two runtimes shared one set of SQLite files: the preview server's workerd, and the fresh `getPlatformProxy()` that every mid-test read-back opened (`e2e/fixtures/platform-db.ts`). When the second collided with the first it was the _server_ that took the loss — `SENTRY_DO SQLite failed; database is locked: SQLITE_BUSY`, then `D1_ERROR: Failed to parse body as JSON, got: Error: internal error` on unrelated requests for a few seconds, then a 30s timeout in whichever test was mid-flight. Fixed in two moves, both test infrastructure. The run keeps its emulated state in `.wrangler/e2e-state` (`e2e/state-dir.ts`) rather than the `.wrangler/state` that `pnpm dev`, `wrangler` and sibling worktrees also open: `e2e/prepare.ts` migrates and seeds it, `playwright.config.ts` passes it as `MINIFLARE_PERSIST_PATH`, and `svelte.config.js` hands that to the adapter's `platformProxy`. And a read-back inside a test now goes through `readLocalDb`, which opens that D1 file with `node:sqlite`, read-only — in WAL mode a reader neither blocks the writer nor is blocked by it, and it sees every committed row — so the run holds exactly one workerd, which `ps` sampled every second through a full run confirms. Measured on the mechanism rather than red/green, the failure being probabilistic: a harness standing in for the server (one miniflare querying D1 continuously) plus three concurrent read-backs failed 14 times in 180 reads over five reps and logged `SENTRY_DO SQLite failed` in one of them; the same harness reading through `node:sqlite` failed 0 times in 180 over five reps. The number to watch is the lock count, not the pass count: every CI run before this logged locks — 2, 4 and 5 events in three _green_ runs, more in the red ones — while both full local runs after it logged zero (they still fail tests for unrelated reasons, see below). Two traps for whoever touches this next: the WAL holds committed rows, so deleting `*-wal`/`*-shm` to clear a lock silently discards the seed — delete all of `.wrangler/e2e-state` instead, which `prepare.ts` rebuilds by itself whenever the migration set changes; and `PUBLIC_SITE_URL` is baked in at build time, so a hand-rolled `pnpm build` without it breaks the subdomain specs in a way that looks like a code regression.

- **Nothing catches a foreign miniflare holding `.wrangler/state`.** Closed by the isolation above rather than by the `prepare.ts` guard this entry asked for: the suite never opens `.wrangler/state` now, so a stray `npm run preview`, a sibling worktree's dev server or a leftover `wrangler` has nothing to contend with it over. One of those zombies did turn up while this was being measured — an orphaned workerd still holding a killed run's `.wrangler/state` half an hour later — and the run beside it was untouched. What is left is a second `pnpm test:e2e` in the same checkout, which collides on port 4173 first, and a preview serving somebody else's build, which `e2e/global-setup.ts` already rejects by comparing `/_app/version.json`.
