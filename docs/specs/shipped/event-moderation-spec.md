# Event Moderation — contentFlag Coverage for the Gig Guide

## Purpose

The unified gig guide (`/events`, community-calendar spec phase 1) shows member
bands' events published by band admins with no staff review, so staff need a
way to hear about and act on problem listings. This extends the existing `contentFlag` moderation
system (member/band profile reports, `/staff/flags` triage queue) to events.

## Decisions

- **Reactive, not proactive.** No staff pre-approval queue. Publishing is
  already gated to band admins; a flag is the kill switch. (Pre-approval was
  considered and deliberately deferred in the community-calendar spec.)

  > **Amended by `docs/specs/shipped/community-events-spec.md`.** This decision
  > originally read "No `pending_review` status and no staff pre-approval
  > queue." The status now exists — community listings need somewhere to sit
  > while staff look at them. What still holds, and what this decision was
  > actually defending, is that **publishing is not gated by default for
  > anyone**. Pre-approval applies only to a member who has had a report upheld
  > against them, and never to band or CMC events.

- **Anyone can report, Turnstile-gated.** The gig guide is public, so the
  report form on `/events/[id]` is public too, protected by the site's existing
  Cloudflare Turnstile pattern (`verifyTurnstile` + `svelte-turnstile` widget).
  Signed-in users get their identity attached automatically; anonymous reports
  are stored with a null reporter and rendered as "Anonymous visitor" in
  triage. Existing member-only profile reporting is unchanged (no Turnstile
  added there).
- **Resolution = dismiss or resolve, with optional unpublish.** Resolving an
  event flag offers an "Also unpublish this event" option that drops the event
  to `draft` (removing it from the public guide, reversible by the band). For
  band events, unpublishing notifies the band's admins in-app and by email,
  including the staff resolution note, so a well-meaning band can fix and
  republish.
- **Full event context in triage.** The flag detail page shows the event's
  title, date, venue/location, band (linked to the directory profile), current
  status, and a link to the public listing — enough to judge without leaving
  the queue.
- **All published events are reportable**, CMC and band alike. The flag
  machinery is source-agnostic; special-casing band-only buys nothing. Draft
  and cancelled events are not reportable (avoids id probing).
- **Feature flag:** everything rides the existing `contentFlags` flag. No new
  flag.

## Schema delta

`content_flag` (src/lib/server/db/schema/flag.ts):

- `entity_type` enum gains `'event'` (type-level only; no CHECK constraint in
  SQLite).
- `reported_by_user_id` becomes nullable to allow anonymous reports; FK
  `onDelete` changes from `cascade` to `set null` so reports survive reporter
  account deletion.

Migrations are generated by the maintainer with drizzle-kit (nullable change is
a SQLite table rebuild).

## Flow

1. Visitor (or member) opens a published event's page, clicks Report, fills
   reason (+ optional details), passes Turnstile, submits.
2. `createFlag` stores the row and notifies all staff in-app — unless a
   `pending` flag already exists for the same event, in which case the row is
   stored without re-notifying staff (spam/noise mitigation; repeat reports
   pile onto the existing queue item).
3. Staff triage at `/staff/flags`: event rows show type "Event" and the event
   title; detail shows the event context card.
4. Staff resolve: dismiss (listing is fine) or resolve, optionally with
   unpublish. Unpublish uses the existing `event-service.unpublish()` (draft +
   `publishedAt` cleared). For `source='band'` events this emits
   `event.unpublished_by_staff`, and a notification listener fans out to the
   band's active owners/admins (`band_event_unpublished` notification type,
   in-app + email by default) with the staff note and a link to the band's
   member page.

## Out of scope (deferred)

- ~~Staff pre-approval / `pending_review` status.~~ Narrowed and shipped for
  community listings only — see the amendment above.
- Per-band or per-event opt-out from the public guide.
- Rate limiting beyond Turnstile (per-IP caps, shadow bans).
- Reporter-facing status updates ("your report was reviewed").
- Automated takedowns (N flags → auto-unpublish).
