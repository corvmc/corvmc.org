# Directory matching

Status: ✅ /member dashboard card

Turns `directory_entry.lookingFor` from a filter chip into a suggestion. `findMatchesFor()` (`src/lib/server/directory/directory-service.ts`) reads the viewer's own direction: `'band'` looks for bands wanting members, `'members'` for members wanting a band, unset asks nothing and the card names the missing field. The match is **my instruments against their needs**, made possible by a `seeking_instrument` tag kind — there was never a `band_instrument` among the three tables `directory_tag` replaced, so a band could say it wanted members but not what for. Instrument or genre overlap qualifies; instrument+genre ranks first, then instrument, then genre. Four exclusions, all reused rather than restated: the listing visibility gates (`memberWhereConditions`/`bandWhereConditions`, including both soft-delete flags), the viewer's own bands, the viewer themselves, and `user_block` in either direction — a match must not become a way around a block DMs already respect. It rides `getMemberDashboard`'s existing `Promise.all` so the page keeps one load-bearing query. Bands say what they need on `/band/[slug]/edit`; the member profile's looking-for boolean became the column itself, so a member assembling a band can point it the other way. Seeded personas: `seeker@`, `bandleader@`, `undecided@`
