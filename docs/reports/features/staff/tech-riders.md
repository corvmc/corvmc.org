# Tech riders

Status: 🔧 /band/{slug}/rider

What a band needs on stage, kept as data rather than as a PDF somebody has to open — and **owned corner by corner**. Each member declares their own gear and the channels it needs; an owner or admin can edit anyone's, and the band's shared kit (a playback rig, spare stands) has a null owner and is admin-only. That split is two remote functions rather than one with a flag: `saveMyRiderElements` takes no owner argument at all and writes against the guard's user, the way `updateMyBandMembership` does, while `saveMemberRiderElements` names one and is guarded at `admin`. Three tables — `rider` (one per band: tech contact, monitor format, notes, and a `confirmedAt` nothing writes yet, for the re-confirm-per-show workflow that comes later), `rider_element` (a thing on the stage, attributed to a member) and `rider_input` (a channel the desk has to find: source, mic preference, +48V, stand, whose monitor mix it feeds). **Channel numbers are derived, never stored**, and the order comes from each item's _kind_ rather than from `sortOrder` — drums, bass, guitars and keys, then vocals, which is the order an engineer reads and the reason two members can edit their own corners without either renumbering the other. A monitor is an element with no inputs, so the mix count is derivable and the stage plot will have something to draw. `providedBy: band | venue`is the backline half: a`venue`item is a request, and the page counts them. **Uploading the rider you already have stays a first-class path**, and is now reachable by every band rather than only premium ones — the`rider`and`stage_plot` `media_attachment`slots and`/api/bands/[id]/media`already existed and were never tier-gated; the only thing missing was a UI outside the premium page editor. A band may keep both, and no read surface silently prefers one. The editor follows the`LineupEditor`shape: local`$state`, ↑/↓ reorder, one hidden JSON field, `sortOrder`re-derived server-side from array position, inserts chunked under D1's 100-parameter cap. Free for every band and on the nav for every role including staff, which is the point — the member who owns the amp is the one who can say what it needs. **The input list** is its own print page at`/band/{slug}/rider/list`: channels numbered in banks of eight, because that is how a console is laid out and how the engineer reading it will patch. A print stylesheet rather than a PDF, following the EPK page and the reports decision record; `/band/{slug}/rider/export`is the CSV, a`+server.ts`because a download needs`Content-Disposition`, guarded by `requireGroupRole`with`allowStaff` and carrying its totals in a comment line. An element with no inputs — a wedge, a backline request — exports with a **blank** channel rather than zero. **`venue.consoleChannels`** is site config with a staff field on `/staff/settings`, and a rider over it says so on both the editor and the list: not a refusal, since the house engineer decides what gets combined, but the "flag what the room cannot do" half of the Production user story, found on the page rather than at load-in. Staff read the whole bill at once on `/staff/events/{id}/production`— a Tech riders card off`event_band`(not`production_slot`, which does not exist) showing channel, phantom, from-us and file counts per act, and leading with how many acts have sent **nothing**, which is the number an advance acts on. **The bill's own input list** is `/staff/events/{id}/inputs`, linked from that card: every act's channels numbered continuously in console order, banded in eights, attributed, with `/staff/events/{id}/inputs/export`for the CSV. It is the check no per-act sheet can run — three acts of twelve pass their own`consoleChannels`test and then do not fit a 24-channel desk. Repeats across acts are **marked, never collapsed**: whether three kicks are one kick is the house engineer's call, so the header carries both the raw count and the count if every repeated source is patched once. **The stage plot** is`x`/`y`percentages on an element — a picture of relative position, so it reads the same in any room, and unrelated to`sortOrder`, which is channel order. Both null means unplaced, which renders as a tray rather than a pile at the origin. Placement follows the same ownership rule as the rest, enforced per element rather than by the guard: a member places their own gear, an owner or admin places anything. A rider edit deletes and reinserts that member's rows, so placements are carried across by label — without it, saving your input list would silently sweep your gear off a plot you were not looking at. **No plotting library**: `docs/reports/library-candidates.md`lists`konva`for this, but a canvas draws pixels rather than focusable controls, so the keyboard path would have to be built beside it — every item here is a real button that arrow keys nudge (ten percent with shift) with a "Place exactly" numeric disclosure as the typed path, which is the rule`SplitBar`states: drag is the affordance, not the mechanism.
