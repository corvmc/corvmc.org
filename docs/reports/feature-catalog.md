# CorvMC Feature Catalog

Last updated: 2026-09-03

Every feature the app ships, what it does, and where it lives. Add a row here when you ship
something — that is phase 8 of
[the feature checklist](../development/conventions.md#the-feature-checklist), and it is how anyone
else finds out the feature exists.

> **History.** This was `parity-report.md`, a Laravel → Svelte feature matrix, until 2026-08-26.
> The legacy Laravel app is no longer active — the server survives only to verify bcrypt for
> un-migrated logins — so there was nothing left to reach parity with. The comparison columns were
> dropped and the file renamed to what it had actually become.

**Status legend:** ✅ Built · 📋 Designed, not built (see the linked spec)

**Not here:** unbuilt ideas live in [`IDEAS.md`](../../IDEAS.md), design intent for unbuilt features
in [`docs/specs/`](../specs), tech debt in [`CHORES.md`](../../CHORES.md), and how the eight core
workflows actually behave in
[development/business-workflows.md](../development/business-workflows.md).

| Groups                     | ✅ /staff/groups            | Clubs and committees. `/staff/groups` is the only place one is created, with its leader appointed in the same step; join policy, joining instructions and listing visibility; roster with applications apart from members; deactivate/reactivate. Publishing fans out to the roster in one batched send on the transactional stream plus chunked in-app rows, latched on `notified_at` so the bus redelivering cannot notify twice; the author, muted memberships and deactivated accounts are excluded in the recipient query, and every email carries a link to the per-group mute (`group_member.notifyAnnouncements`), which the global `announcement` preference cannot express. **Sessions** are a program's events: `createGroupEvent()` is the first path outside the staff panel that reserves the room, and it holds it _for the event_ (`bookerType: 'event'`) rather than booking it as the group, so it is free and touches no credit ledger. `event_group` carries which groups' pages an event appears on, distinct from `event_band`'s credit on the bill. **Documents** are a club and committee file store — a band keeps its rider and stage plot in the public `media` slots instead, and `file-service` refuses one outright. | Projects                   | ✅ /staff/projects          | A body of work with a budget and an owner — the container work orders, contractor jobs, purchase orders, acquisitions and events hang off by a nullable `project_id`. Events point at projects and never the reverse, so one shape serves a facility improvement (no events), a produced show (one) and a festival (many). `groupId` is the owning committee, enforced in the service because a CHECK cannot cross tables; `suggestionId` closes the member loop, with a partial unique index for one project per suggestion, and a status change writes both in one `db.batch`. **Burn is derived, never stored** — summed over the ledgers that already hold the atoms and returned as two columns that are never added: cash that left the account, and contributed value. Contributed is itself **two figures that are never added to each other**: impact value over every approved hour at `volunteer.hourValueCents`, and recognizable contributed services over specialized hours only, each at its role's own `market_rate_cents` — they overlap, since a donated engineer's hour is in both, so the DTO carries no combined total. | Tech riders                | 🔧 /band/{slug}/rider       | What a band needs on stage, kept as data rather than as a PDF somebody has to open — and **owned corner by corner**. That split is two remote functions rather than one with a flag: `saveMyRiderElements` takes no owner argument at all and writes against the guard's user, the way `updateMyBandMembership` does, while `saveMemberRiderElements` names one and is guarded at `admin`. Three tables — `rider` (one per band: tech contact, monitor format, notes, and a `confirmedAt` nothing writes yet, for the re-confirm-per-show workflow that comes later), `rider_element` (a thing on the stage, attributed to a member) and `rider_input` (a channel the desk has to find: source, mic preference, +48V, stand, whose monitor mix it feeds). **Channel numbers are derived, never stored**, and the order comes from each item's _kind_ rather than from `sortOrder` — drums, bass, guitars and keys, then vocals, which is the order an engineer reads and the reason two members can edit their own corners without either renumbering the other. #### What sends, and what deliberately does not

**Sending:** reservation reminder (upcoming), reservation confirmation reminder (unconfirmed),
band invitation, band invitation accepted, contact form submission, ticket purchase confirmation +
receipt, event cancellation to ticket holders, and the volunteering set (Phase 1 hour-log
notifications plus `volunteer_shift_reminder`, `volunteer_shift_completed`,
`volunteer_shift_feedback`, plus `volunteer_shift_claimed` / `volunteer_shift_confirmed` /
`volunteer_shift_dropped` — the three moments a place on a shift changes hands, which
produced no signal at all before).

**Deliberately not sending**, with the reason:

- Event created/published/cancelled **to the organizer** — self-confirmation noise; they just did it
- Membership renewal reminders — Stripe sends these natively
- Membership expired / welcome / deactivated — low-signal
- Reservation created/confirmed/cancelled lifecycle — the member just took the action in-app; a
  toast is enough

**Still open:** event reschedule to ticket holders (needs event update detection); daily admin
reservation digest (probably a dashboard widget, not an email); rehearsal attendance request and
rehearsal reminder (wait on rehearsal-module work that has not been scoped).

confirmation-reminders → reservation-reminders in order.

### Event-driven architecture

Services fire typed domain events via `emittery`. Listeners handle side effects (notifications,
cross-module reactions), registered explicitly at startup in `hooks.server.ts`.

| Concern               | Status                    | Notes                                                                                           |
| --------------------- | ------------------------- | ----------------------------------------------------------------------------------------------- |
| Event bus             | ✅ `emittery`             | Typed event map, async-native, single emitter instance                                          |
| Checkout fan-out      | ✅ Via emittery           | Migrated from callback registry to the domain event bus                                         |
| Notification dispatch | ✅ Dispatcher + listeners | Listeners check user preferences, route to email (Postmark) and in-app channels                 |
| Activity logging      | —                         | Not built. The closest designed thing is `docs/specs/audit-log-spec.md` (staff account actions) |
| Lock code management  | ✅ Cron-based             | Cron provisions daily rather than per-event                                                     |

### Background processing

No job queue. Postmark API calls are fast enough to fire-and-forget from event listeners, and the
lock code work is handled via cron. Listeners that call external APIs should not block the request —
fire without awaiting, with `.catch()` piped to Sentry. If fan-out to many recipients becomes a
latency problem (e.g. notifying all ticket holders of a cancellation), that is the point to consider
a queue — not before.

  `band_page_config`

- **media** — `media`, `media_attachment`

- **inventory** — `equipment_category`, `inventory_item`, `inventory_asset`, `stock_movement`, `inventory_loan`, `inventory_location`, `acquisition`, `acquisition_line`, `purchase_order`, `purchase_order_line`

  `inbox_group_read`, `inbox_channel_config`

  `volunteer_certification`, `member_certification`, `volunteer_role_certification`

`group` is the `band` table renamed in place (#267) — `group.id` is `band.id`, so every foreign key
still points at the same row. `docs/specs/groups-spec.md` splits it further into `group` +
`directory_entry` + `band_site` + `contact`; that work has not started. Productions would add five
more (`venue`, `production`, `production_slot`, `production_task`, `production_expense`) plus an
`event.venueId` column.

## Feature flags

Three flags, all defaulting to **off**, toggled from Staff Settings → Features — except
`directMessages`, which was never added to that tab and so has never been switchable at all.
`bandPremium` was the fourth until it **launched**: the guards came out rather than being switched
on, so band sites answer on `band_site.tier` alone.
`bandAudio` gates the music storefront and `cmcRadio` the station; both were added with toggles, and
`cmcRadio` exists specifically so the radio can wait for enough bands to opt in. `/staff/music` is
deliberately **not** behind either, because the question the toggle gates on cannot be answered from
behind it. The
whole system is being retired in favour of feature branches; see
[the ledger](../plans/feature-flag-retirement.md).

The groups module (`groups`, `groupEvents`, `announcements`) and `groupFiles` were retired without
being launched, then relaunched separately in #516: the flags are gone, the routes answer
unconditionally, and the nav entries that reach them — "My Groups" in the member panel, Announcements
in the band panel, and a public link to `/groups` that never existed before — are back. Source of truth is
`ALL_FLAGS` in `src/lib/server/feature-flags.ts`; values are `feature.*` keys in the site config KV
store.

**Flags gate the member, band and public surfaces only — the staff panel deliberately ignores them**
(`src/routes/staff/nav-items.ts`). Staff can set a feature up (configure channels, comp a band,
stage help articles, draft a campaign) before it is switched on for everyone else, and can keep
administering it if it is switched back off. Member and public remote functions call
`requireFeature()`, which throws 404 when disabled; staff queries and forms are guarded by
`requireStaff()` alone.

| Flag             | Feature                 | What it gates                                                                            |
| ---------------- | ----------------------- | ---------------------------------------------------------------------------------------- |
| `directMessages` | Member↔member messaging | The DM half of `/member/messages` — member↔staff portal chat in the same UI is not gated |
| `bandAudio`      | Releases and storefront | `/band/[slug]/music`, `/music/**`, and the Releases nav row                              |
| `cmcRadio`       | The station and player  | `/radio` and the site-wide player                                                        |

## Library decisions

Preference is for small, focused packages over frameworks.

| Concern              | Library                          | Why                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Email transport      | `postmark`                       | Official SDK, well-typed, direct integration                                                                                                                                                                                                                                                                                                                                                                     |
| Email templates      | Hand-rolled HTML                 | `mjml` was dropped; the CMC brand shell is plain HTML with dark-mode + mobile media queries                                                                                                                                                                                                                                                                                                                      |
| SMS                  | `twilio`                         | Official SDK if/when the SMS channel is built                                                                                                                                                                                                                                                                                                                                                                    |
| Domain event bus     | `emittery`                       | Async-native (listeners can do I/O without blocking), strong TypeScript generics, ESM-only (fine for SvelteKit)                                                                                                                                                                                                                                                                                                  |
| Recurrence rules     | `rrule`                          | RFC 5545 RRULE parsing/generation with timezone support via luxon. Used for recurring reservation scheduling                                                                                                                                                                                                                                                                                                     |
| Dates                | `@internationalized/date`        | Already installed for the mini-calendar date-jumper; no calendar UI package was needed                                                                                                                                                                                                                                                                                                                           |
| HTML sanitizing      | `js-xss`                         | Sanitizes band-site blocks at save + render — replaced a no-op DOMPurify+linkedom setup                                                                                                                                                                                                                                                                                                                          |
| Error tracking       | `@sentry/sveltekit`              | First-class SvelteKit integration, auto-instruments load functions and routes. Also provides Sentry Crons for scheduled job monitoring                                                                                                                                                                                                                                                                           |
| Image crop/resize    | `svelte-easy-crop` (client-side) | Browser-based crop UI + canvas resize before upload. User selects and frames the image, client resizes to target dimensions, uploads the processed result. No server-side image processing needed                                                                                                                                                                                                                |
| File uploads         | None — the R2 binding            | `src/lib/server/storage.ts` calls the Worker's own `R2Bucket` binding directly; there is no S3 SDK in `package.json`. This row named `@aws-sdk/client-s3` for a long time and was simply wrong — worth knowing, since it sent a reader looking for a dependency that would have to be added rather than used. `@aws-sdk/s3-request-presigner` would be the thing to add if client-direct uploads are ever wanted |
| In-app notifications | Hand-rolled                      | `notification` table via Drizzle, SSE from a SvelteKit `+server.ts` for real-time delivery. Novu/Knock are overkill and have React-only client components                                                                                                                                                                                                                                                        |
| Background work      | Detached promises                | Fire-and-forget with `.catch()` piped to Sentry. Add `p-queue` if concurrency control is needed later. No Redis/BullMQ                                                                                                                                                                                                                                                                                           |

**Not using:**

- `sharp` — native binary, incompatible with Cloudflare Workers
- `svelte-email` — abandoned (last update 2023)
- `@react-email/render` — adds React as a dependency for email templates
- `uploadthing` — stale Svelte support, adds hosted service dependency
- Novu / Knock — hosted notification platforms with React-only UI, overkill for this app
- BullMQ — requires Redis, unnecessary when detached promises suffice

## Image delivery

Cloudflare Image Transformations serve every uploaded image through `/cdn-cgi/image` off the R2
custom domain. [`getPublicUrl()`](../../src/lib/server/storage.ts) mints one canonical transform URL
per key (image formats only — PDFs fall through untransformed), and
[`imageSrc()`](../../src/lib/utils/images.ts) narrows it to a per-component size ladder with
`srcset`/`sizes` at render. Upload keys carry a random token
([`mediaKey()`](../../src/lib/server/storage-keys.ts)) so replacing an image can't serve a stale edge
cache. "Resize images from this zone" is enabled on the `corvmc.org` zone and `/cdn-cgi/image/` is
intercepted on the `media.corvmc.org` R2 custom domain (verified 2026-08-16), so `R2_TRANSFORM_URL`
uses a bare-key source.

The one-image-per-entity model it sits on is still ad hoc — see the media-management entry in
[`CHORES.md`](../../CHORES.md), now designed in [`docs/specs/shipped/media-spec.md`](../specs/shipped/media-spec.md).
